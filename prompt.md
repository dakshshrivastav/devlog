# Build prompt for Devlog

Paste everything below the line into your coding assistant (Claude Code, Cursor, etc.). Put `idea.md` in the project folder first, so the assistant can read it.

---

You are helping me build **Devlog**, a hackathon project. Read `idea.md` in this folder first. It is the specification. If this prompt and `idea.md` disagree, ask me.

## Goal

Devlog turns a build session (voice memo or video, photos, git history) into documentation:

- `README.md`
- `OBSERVER_NOTES.md` (third-person notes)
- `diagrams/*.mmd` (Mermaid flowcharts generated by the model)
- `GAPS.md` (questions the docs still need answered)

The model is **Gemma 4**. Speech-to-text is **ElevenLabs Scribe v2**, with **local Whisper** as a fallback.

## Hard limits

- Build the smallest working version first. Follow the build order below.
- Language: Python 3.11+. CLI first. The only UI is one small local page for live mode (build order, step 10).
- License: MIT. The repository must be public-ready.
- Do not invent API details. For the Gemini API (Gemma 4) and the ElevenLabs API, read the current official docs or SDK source before you write the call.
- If you cannot find the API information you need (for example a model ID, a parameter name, or how the realtime connection works), stop and ask me to add the relevant documentation to the project folder, for example `docs/elevenlabs/` and `docs/gemini/`. Say exactly what you need. Do not guess. Continue only after the files are there.
- Read API keys from environment variables (`GEMINI_API_KEY`, `ELEVENLABS_API_KEY`). Never write keys to files or logs.
- Do not claim anything works until you have run it. Report what you ran and what the output was.

## Inputs

A capture folder:

```
capture/
  audio/        voice memos (.m4a, .wav, .mp3)
  photos/       images (with EXIF time if present)
  notes.txt     optional dictated notes (e.g. from Wispr Flow)
  keyterms.txt  optional: one project word per line (part names, tools)
```

Plus the git repository of the project (path given on the command line).

## Pipeline

1. **transcribe**: send each audio file to ElevenLabs Scribe v2. Send `keyterms.txt` if the API supports it (check the docs). Save the raw JSON, with word timestamps, to `out/transcripts/`. Option `--stt whisper` uses a local Whisper model instead. The tool must run end to end with no ElevenLabs key.
2. **timeline**: build one list sorted by time. Items: speech segments, photos, notes, git commits. Give every item a stable source tag: `[voice 02:14]`, `[photo 3]`, `[note 5]`, `[commit a1b2c3]`. Save it as `out/timeline.json`.
3. **generate**: call Gemma 4 with the timeline and the images. Make one call per output. See "Prompts for Gemma 4" below.
4. **validate**: run the checks below on every output. Retry once on failure. If it still fails, drop the output and add a line to `GAPS.md`.
5. **write**: save to `out/`.

## Live mode

Live mode is a second command: `devlog live`. The user talks into a microphone. The notes and a flowchart update while the user talks.

1. Stream microphone audio to ElevenLabs Scribe v2 Realtime. Read the docs first. Fallback: local Whisper on short chunks (`--stt whisper`).
2. Save every raw transcript chunk to `out/live/raw.jsonl`, in full, with start and end times. Never edit it.
3. For each new chunk, call Gemma 4 with: the current graph (boxes, arrows, clusters), the active cluster, the last few live notes, and the new chunk. Gemma 4 returns JSON: `{"note": string or null, "ops": [...]}`. See `prompts/live.md`.
4. Validate the JSON. Drop a bad op and log it. Never crash the session on a bad response.
5. Apply the ops to the graph state (`out/live/graph.json`). Append each applied op to `out/live/graph_history.jsonl`, with its source span and time.
6. Write `out/live/graph.mmd` (Mermaid) after every change. Append the note to `out/LIVE_NOTES.md`, with its raw span, for example `[live 14:02-14:09]`.
7. A small local page (served by Python, no hosting) polls `graph.mmd` and `LIVE_NOTES.md` and shows them. It draws the graph with Mermaid in the browser. If you need a JavaScript file for this, ask me to add it to the folder or tell me which one to download. Do not rely on a network connection at run time if you can avoid it.
8. If Gemma 4 is slow or fails, keep saving raw chunks. Process the backlog later.
9. Sidetracks: every box belongs to a cluster (one topic). When the speaker jumps to a different topic, Gemma 4 starts a new cluster in the same graph, and new boxes go there. When the speaker returns to an earlier topic, Gemma 4 switches to that cluster. In `graph.mmd`, draw each cluster as a Mermaid `subgraph`.
10. Unify step: when the speaker is done (end of session, or on `devlog unify`), make a separate Gemma 4 call with the full graph and the notes of every cluster. See `prompts/unify.md`. It finds unifying points between clusters: shared things, boxes that name the same thing, or stated dependencies. It links them. If two clusters have no real connection, it leaves them separate and adds a gap question. Draw cross-cluster links after the subgraphs.
11. At the end of the session, add the live notes and graph history to the timeline, with source tags, so the later documents can use them.

Op examples (you define the final schema, keep it small):

```
{"op": "add_node", "id": "relay", "label": "Relay"}
{"op": "add_edge", "from": "esp32", "to": "relay", "label": "pin 5", "inferred": false}
{"op": "rename_node", "id": "sensor", "label": "Temperature sensor"}
{"op": "remove_edge", "from": "esp32", "to": "sensor"}
{"op": "start_cluster", "id": "power", "label": "Power supply"}
{"op": "switch_cluster", "id": "wiring"}
{"op": "merge_nodes", "keep": "relay", "merge": "switch", "reason": "same part"}
```

Each box has a `cluster` field. `merge_nodes` never deletes history. Both original names stay in `graph_history.jsonl`.

## Rules for the generated text

- A claim needs a source tag. No tag, no claim.
- A guess must be marked "(guess)".
- A missing fact goes into `GAPS.md` as a question. Never invent it.
- Observer notes: third person, past tense, "the builder". No "I", "we", "my", "our". Say how each fact is known ("said", "shown in photo", "committed"). No feelings or motives that nobody stated.
- Diagrams: every box and arrow maps to a source. Inferred links are dashed and labeled "inferred". The Mermaid text must parse.
- Live notes: the shortest text that keeps the meaning. Keep names of things, actions, numbers and units, negations ("not", "never"), and which thing connects to which. Drop filler and repeats. Never add a fact that the raw chunk lacks. No fact in the chunk, no note.
- Graph ops: only name things the speaker named or that already exist in the graph. An unstated link is marked inferred. A correction by the speaker is a rename or remove op, and the old state stays in the history file.
- Sidetracks: a new topic gets a new cluster. A return to an old topic reuses the old cluster. Do not link clusters during the session unless the speaker states the link.
- Unify step: link clusters only with a source. A link that nobody stated is marked "inferred". Never force a link between unrelated topics. Never delete a box or an arrow.
- The raw transcript is never changed.

## Build order (stop and report after each step)

1. Project skeleton, `LICENSE` (MIT), `pyproject.toml`, empty `README.md`.
2. `transcribe.py` with both backends. Test with a short audio file.
3. `timeline.py`. Test with a small git repo and 2-3 photos.
4. `generate.py` for `README.md` only, with source tags. Test it.
5. Validators (source tags, first-person check, Mermaid parse).
6. `OBSERVER_NOTES.md` and `diagrams/system.mmd`.
7. `GAPS.md`.
8. Tests (see below).
9. Real README: what it is, setup, usage, a demo section, a "How Gemma 4 is used" section, and a "Status" section with **verified** and **not verified** items.
10. Live mode: `devlog live`, as described above. Build it in this order: raw transcript streaming and saving; condense step with `prompts/live.md`; graph ops and history; Mermaid output; the local page.
11. After that: video input (ffmpeg audio + sampled frames), spoken gap questions (ElevenLabs text-to-speech), `DEVLOG.md`, `BOM.md`.

## Tests

Write pytest tests. Use fixtures, not live API calls, where possible.

- **C1**: every claim line in a generated README has a source tag.
- **C2**: plant a false detail in a test timeline. The output must not state it as fact.
- **C3**: remove one known fact from a test timeline. It must appear in `GAPS.md`.
- **C5**: a spoken note near a commit time attaches to that commit.
- **C6**: the pipeline runs with `--stt whisper` and no ElevenLabs key.
- **C8**: every saved `.mmd` file parses.
- **C9**: `OBSERVER_NOTES.md` has zero matches for "I", "we", "my", "our" (whole words).
- **C11**: for test chunks, every name, number and negation in the raw chunk appears in the live note.
- **C12**: a chunk that does not mention a part produces no node for that part. Every op id maps to the chunk or to the existing graph.
- **C13**: every live note has a raw span. The raw transcript file is unchanged after the session.
- **C14**: make the Gemma 4 call fail on purpose. The raw transcript is still complete, and the backlog is processed later.
- **C15**: a spoken correction changes the graph, and the old state is in `graph_history.jsonl`.
- **C16**: test chunks go topic A, then topic B, then back to A. B gets its own cluster. The return to A reuses the old cluster, and no new cluster is created for it.
- **C17**: two unrelated topics stay unlinked after the unify step, and a gap question is created.
- **C18**: every cross-cluster link has a source. Unstated links are marked inferred. Nothing is deleted.

For tests that need Gemma 4, mark them `@pytest.mark.live` so they can be skipped.

## Prompts for Gemma 4

Store these as files in `prompts/`. Put the timeline in the user message, as JSON, with the source tags.

### `prompts/readme.md`

```
You write a README for a software or hardware project. You are given a timeline of
a build session: speech transcripts, photos, notes, and git commits. Each item has
a source tag.

Rules:
- State a fact only if an item in the timeline supports it. End each statement with
  its source tag, for example [voice 02:14] or [commit a1b2c3].
- If you are unsure, write "(guess)" after the statement.
- If a section needs a fact that the timeline does not contain, do not write the
  fact. Write "GAP: <question>" instead.
- Use plain, short sentences.
- Sections: What it is, How it works, Setup, Usage, Known problems.
- Output Markdown only.
```

### `prompts/observer.md`

```
You write observer notes about a build session. You are given a timeline with source
tags. Write as a neutral outside observer.

Rules:
- Use the third person and the past tense. Call the person "the builder".
- Never use "I", "we", "my", or "our".
- Start each note with how the fact is known: "The builder said...", "The photo
  shows...", "The commit changes...".
- End each note with its source tag.
- Do not state feelings or motives that nobody stated.
- If speech and a photo disagree, write both and add "(conflict)".
- Order the notes by time.
- Output Markdown only.
```

### `prompts/diagram.md`

```
You draw a diagram as Mermaid text. You are given a timeline with source tags and a
diagram type: "system" or "steps".

Rules:
- Output only Mermaid code. No explanation. No code fences.
- Use `flowchart TD`.
- Every box and every arrow must be supported by an item in the timeline.
- Put the source tag in a Mermaid comment (%%) on the line before the box or arrow.
- Draw a link as a dashed arrow (-.->) and label it "inferred" when no item states it.
- If the timeline does not support a diagram, output exactly: NO_DIAGRAM
```

### `prompts/gaps.md`

```
You list what the documentation is missing. You are given a timeline and a draft
README. List questions that a reader of the README would need answered and that the
timeline does not answer.

Rules:
- One question per line.
- Ask about things such as: why a part or tool was chosen, setup steps, versions,
  wiring or connections, what failed and how it was fixed.
- Do not answer the questions.
- At most 10 questions. Put the most important first.
- Output a Markdown list only.
```

### `prompts/live.md`

Put the current graph (JSON, with clusters), the active cluster, the last few live notes, and the new chunk (with its time span) in the user message.

```
You turn live speech into a very short note and changes to a flowchart.

You are given: the current graph (boxes, arrows, and clusters), which cluster is
active, the last few notes, and a new chunk of transcribed speech with its time span.

Rules for the note:
- Write the shortest text that keeps the meaning.
- Keep: names of things, actions, numbers and units, negations (not, never, no longer),
  and which thing connects to which.
- Drop: filler words, repeats, and words that add no fact.
- Do not add any fact that is not in the chunk.
- If the chunk has no fact (for example "um, let me think"), set "note" to null.

Rules for graph changes ("ops"):
- Allowed ops: add_node, add_edge, rename_node, remove_node, remove_edge,
  start_cluster, switch_cluster.
- If the speaker mentions a thing that already exists in the graph, use the existing
  box. Do not make a duplicate.
- Only name things that the speaker named.
- If the speaker corrects something ("no wait, ..."), use rename or remove ops.
- If a link is not stated but is likely, use add_edge with "inferred": true.
- If the chunk changes nothing in the graph, return an empty list.

Rules for sidetracks:
- Every box belongs to one cluster. A cluster is one topic.
- New boxes go into the active cluster.
- If the speaker jumps to a different topic (a sidetrack), do not attach the new
  boxes to the old topic. Use start_cluster with a short label, then add the new
  boxes to it. Do not link the two clusters yet.
- If the speaker returns to an earlier topic ("anyway, back to the relay"), use
  switch_cluster to go back to the existing cluster. Do not start a new one.
- Link two clusters now only if the speaker states the link. Otherwise, wait for
  the unify step.

Output JSON only: {"note": string or null, "ops": [ ... ]}
```

### `prompts/unify.md`

Put the full graph (JSON, with clusters), the live notes of every cluster, and their raw transcript spans in the user message.

```
You link separate topics in one flowchart. You are given the full graph. It has
several clusters. Each cluster is one topic. You are also given the live notes and
the raw speech spans for each cluster.

Task: find unifying points. A unifying point is a place where two clusters share
or depend on the same thing.

Allowed changes:
- add_edge between boxes in different clusters, when the speech supports a relation.
- merge_nodes, when two boxes in different clusters name the same thing.
- add_node for a shared thing that the speaker named and that both clusters use.

Rules:
- Each change needs a source: the raw span or note that supports it.
- If a link is likely but nobody stated it, set "inferred": true.
- If two clusters have no real connection, leave them separate. Do not force a link.
  Add one line to "gaps" instead: a question for the speaker, such as
  "How does X relate to Y?".
- Never delete a box or an arrow.

Output JSON only: {"ops": [ ... ], "gaps": [string]}
```
